# 機器人記憶體架構計畫 (Bot Memory Architecture Plan)

## 概觀 (Overview)

本計畫旨在為機器人添加一個五層記憶體系統，同時將 Laya 定義為決策閘門，而非最終的事實來源。該系統必須保持可稽核性：每條長期記憶必須能追溯至特定片段 (episode)，且每一次的覆蓋或遺忘動作都必須有理由。

記憶體系統還必須防止主聊天路徑產生過多的遠端 LLM 或向量嵌入 (embedding) 請求。記憶體強化僅在不會導致助手觸發提供者保護機制（如 HTTP 429 速率限制）時才有用。預設行為應優先回答使用者，隨後在背景執行有界且具備重試安全性的記憶體工作。

## 規劃表 (Planning Table)

| 階段 | 記憶體層級 | 目標 | 主要交付物 | Laya 的角色 | 儲存方式 | 驗證 |
|---|---|---|---|---|---|---|
| 1 | 第 2 層：片段記憶 (Episodic Memory) | 記錄每次互動中發生的事情。 | 新增 `memory.py`；建立 SQLite 表格以記錄事件；記錄使用者、助手、工具調用、工具結果、Laya 決策、錯誤、時間戳。 | 分類事件是常規的、風險的、失敗的，或潛在值得後續提取的。 | SQLite `episodes`, `episode_events`。 | 插入/查詢的單元測試；確認每次 CLI 輪詢都會寫入事件。 |
| 2 | 第 1 層：工作記憶 (Working Memory) | 當訊息歷史增長時，保持活動上下文有用。 | 新增訊息修剪和摘要注入；保留近期輪詢並壓縮舊輪詢。 | 在壓縮前決定舊上下文中是否包含值得保留的事實或程序。 | 記憶體內 `messages`；SQLite 中可選的摘要行。 | 上下文壓縮邊界和摘要放置的測試。 |
| 3 | 第 3 層：語義記憶 (Semantic Memory) | 儲存持久的事實、偏好、實體和關係。 | 新增 SQLite 三元組類表格：`主體`, `謂語`, `客體`, `信心度`, `來源事件 ID`, `建立時間`, `更新時間`, `過期時間`, `被取代者`。 | 閘門角色：決定片段中是否包含持久事實、偏好或衝突。 | SQLite `semantic_memories`。 | 插入、更新、衝突標記、來源追溯的測試。 |
| 4 | 檢索 (Retrieval) | 在回答前使用記憶體，且不產生無界的向量嵌入擴散。 | 在 `run_agent` 前添加檢索步驟；先使用廉價的 SQLite/詞彙過濾；僅對小規模候選集執行向量排序；將簡潔的記憶體上下文注入訊息。缺失的記憶體嵌入不得在每次行迭代中同步補全。 | 僅在廉價過濾減少候選集後，才對記憶體與當前使用者請求的相關性進行排序。 | SQLite 查詢, 快取嵌入, 記憶體內上下文。 | 驗證相關記憶體被包含、陳舊/被取代記憶體被排除，且單次輪詢有固定的遠端嵌入呼叫上限。 |
| 5 | 第 4 層：程序記憶 (Procedural Memory) | 記住可重複使用的成功工作流，而無需每次比較都呼叫 LLM。 | 新增 `procedures` 表，包含 `任務類型`, `上下文模式`, `步驟`, `成功次數`, `失敗次數`, `最近成功時間`, `信心度`；先使用詞彙/精確匹配比較新候選，僅對小型模糊候選集使用 LLM 相似度。 | 決定完成的片段是否代表一個可重複使用的程序以及是否成功。 | SQLite `procedures`，連結至來源片段。 | 程序建立、成功/失敗更新、按任務類型檢索，以及跳過 LLM 相似度或觸發速率限制時的回退行為測試。 |
| 6 | 第 5 層：遺忘 (Forgetting) | 防止陳舊、矛盾或低價值記憶體的累積。 | 新增遺忘策略：過期、取代、信心度衰減、封存理由、手動清除掛鉤。遺忘預設必須是確定性的，且在面向使用者的輪詢中不應要求遠端 LLM 呼叫。 | 候選評判員：識別衝突、過時事實、一次性上下文或應過期的記憶體。 | SQLite 欄位：`archived_at`, `archive_reason`, `expires_at`, `superseded_by`。 | 衝突替換、過期過濾、審計追蹤保留，以及常規策略運行時零遠端請求的測試。 |
| 7 | 回顧與可觀測性 (Review and Observability) | 使記憶體行為可調試且感知速率限制。 | 新增命令或輔助函數，用於檢查近期片段、語義事實、程序、封存記憶體、記憶體隊列深度、遠端請求預算使用情況、回退次數以及 429/重試事件。 | 將可疑或低信心度的記憶體決策分類以供回顧。 | SQLite 讀取 API；可選的 CLI 輔助工具。 | 檢查輸出、請求預算日誌以及提供者 429 後優雅降級的手動煙霧測試和單元測試。 |

## Laya 的責任邊界 (Laya Responsibility Boundary)

| 決策領域 | 由 Laya 決定？ | 最終寫入者 | 備註 |
|---|---:|---|---|
| 片段是否可能包含持久事實 | 是 | 記憶體服務 | Laya 僅產生候選信號。 |
| 精確的語義事實內容 | 部分 | LLM 或解析器 + 記憶體服務 | Laya 不應是唯一的提取者。 |
| 工作流是否可重複使用 | 是 | 程序記憶體服務 | 程序步驟應來自實際片段/工具日誌。 |
| 一條記憶體是否與另一條衝突 | 是 | 記憶體服務 | 規則決定取代和封存。 |
| 是否永久刪除記憶體 | 否 | 明確策略或使用者操作 | 優先選擇封存而非硬刪除。 |
| 陳舊記憶體是否應被忽略 | 是 | 檢索層 | 檢索必須過濾過期和被取代的行。 |
| 是否在記憶體強化上花費遠端 LLM 預算 | 否 | 請求預算策略 | 策略必須保護主助手回應不受記憶體相關 429 的影響。 |

## 微軟 Agent Memory 後續路線圖 (Microsoft Agent Memory Follow-Up Roadmap)

本節記錄在將當前項目與微軟的 agent-memory 教學對比後的後續改進。目前的實現已涵蓋核心形態：工作記憶壓縮、片段事件日誌、語義三元組、程序記憶、檢索注入、背景回顧和確定性遺忘。後續工作應專注於記憶體質量、結構化檢索以及使儲存的記憶體更容易治理。

### 當前實現狀態 (Current Implementation Status)

在本計畫後已實現：

- 壓縮後的工作記憶摘要可進入長期回顧管線，並從摘要中進行去重安全的語義提取。
- 語義記憶現在具有明確的 `memory_type`（記憶體類型）和 `scope`（範圍），提取/檢索時會保留這些欄位。
- 語義記憶能透過 `entities`（實體）、`entity_aliases`（實體別名）、`subject_entity_id` 和 `object_entity_id` 連結到標準化實體。
- 語義更新為一等公民：新候選可以增加、強化、取代、矛盾或忽略現有記憶，並附帶審計事件。
- 程序記憶可檢索至提示詞上下文，且程序結果可從後續工具使用中追蹤。
- 治理命令現在涵蓋回顧候選、事實、低信心事實、衝突、程序、封存/確認/矛盾/取代、匯出和匯入。
- 前台檢索和背景回顧的請求預算已被記錄。
- 語義嵌入追蹤 `embedding_updated_at`；提供有界的維護命令以補全缺失的嵌入。
- 記憶體可觀測性包含 `memory-health`，總結請求預算、封頂的記憶體操作、429 錯誤和嵌入補全隊列深度。

已完成的後續工作：

- 持久化背景任務現在透過 SQLite `memory_jobs` 涵蓋 `memory_review`（記憶體回顧）和 `embedding_backfill`（嵌入補全）隊列，使排隊工作能在進程重啟後生存。
- 全域提供者的 429 冷卻/退避狀態儲存在 SQLite `memory_provider_state` 中；背景工作在下次遠端嘗試前會遵守 `Retry-After`。
- 嵌入補全可透過 `stale_before` 刷新陳舊嵌入，而不僅僅是填充缺失嵌入。
- 檢索會記錄 `memory_retrieval_stats` 中跳過的缺失嵌入補全次數，且 `memory-health` 會總結這些計數。
- 安裝可選依賴後，完整的倉庫測試發現目前均能通過。

### 優先級 1：將壓縮的工作記憶提升至長期回顧 (Promote Compacted Working Memory Into Long-Term Review)

目前行為在壓縮上下文可能包含持久事實或程序時會記錄 `working_memory_preservation_candidate`，但記憶體回顧管線僅處理 `memory_review_candidate` 事件。這意味著有用資訊在壓縮時被注意到，但未能被提取到語義或程序記憶中。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 標準化保留候選 | 將 `working_memory_preservation_candidate` 轉換為可回顧的語義/程序候選，或讓 `process_memory_review_candidates` 同時處理兩種事件類型。 | 被分類為 `semantic`、`procedure` 或 `both` 的壓縮摘要能產生與普通候選相同的回顧結果形態。 |
| 安全地從摘要提取 | 添加提取路徑，使用壓縮摘要作為源文本，同時保留對片段和摘要事件的追溯性。 | 從摘要建立的語義記憶能指向 `working_memory_summary` 或保留事件。 |
| 避免重複提取 | 將從摘要衍生的記憶體與從同一片段已提取的記憶體進行去重。 | 測試證明單次輪詢不會從原始訊息和壓縮摘要中建立重複的事實。 |

### 優先級 2：添加明確的記憶體類型和範圍 (Add Explicit Memory Types and Scopes)

微軟將長期記憶分為專業形式，如人格 (persona)、實體 (entity)、工作流/片段 (workflow/episodic) 和使用者偏好 (user preferences)。目前的 `semantic_memories` 表可以用三元組表示這些，但檢索無法區分穩定的使用者偏好、項目事實或助手人格規則。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 添加記憶體類型元數據 | 為語義記憶添加 `memory_type` 和 `scope` 欄位，值如 `user_profile`, `project_fact`, `agent_persona`, `entity_fact`, `task_fact`。 | 現有行以預設類型遷移，且測試能按類型過濾/檢索。 |
| 更新語義提取提示詞 | 要求提取器在主體/謂語/客體/信心度之外，為每個三元組分類類型和範圍。 | 解析的 LLM 輸出儲存類型化記憶，且在類型缺失時能優雅回退。 |
| 優先考慮穩定的人格記憶 | 當信心度相當時，檢索應優先選擇相關的 `user_profile` 和 `project_fact` 記憶，而非暫時的任務事實。 | 提示詞上下文按類型對記憶進行分組，並優先包含高價值的個人資料事實。 |

### 優先級 3：引入實體感知結構化記憶 (Introduce Entity-Aware Structured Memory)

目前的三元組儲存是一個好的開始，但實體記憶仍是隱式的。輕量級實體層將使機器人理解多個事實是指向同一個項目、提供者、模型、文件或使用者偏好。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 添加實體記錄 | 為標準化名稱、標籤、種類和來源事件建立 `entities` 和可選的 `entity_aliases` 表。 | 提取的事實能將主體/客體文本連結到穩定的實體 ID。 |
| 將語義三元組連結到實體 | 添加可為空的 `subject_entity_id` 和 `object_entity_id` 欄位或關聯表。 | 檢索能透過別名找到事實，而不僅僅是精確文本匹配。 |
| 建立以實體為中心的上下文 | 添加檢索模式，在格式化提示詞上下文前按實體對相關記憶進行分組。 | 詢問關於項目/模型/提供者的資訊時，會返回一組緊湊的連接事實。 |

### 優先級 4：使記憶體更新成為一等公民 (Make Memory Updates First-Class)

微軟將記憶體管理描述為「提取 + 更新」管線。目前的系統提取記憶並稍後透過遺忘策略解決衝突。更強的更新步驟應在插入前決定新記憶是增加、強化、取代還是矛盾現有記憶。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 添加更新決策服務 | 給定一個候選三元組，檢查具有相同主體/謂語或連結實體的活動記憶，並選擇 `add`, `reinforce`, `supersede`, `contradict`, 或 `ignore`。 | 測試涵蓋相同事實強化、偏好變更取代、矛盾封存和低信心忽略。 |
| 使用現有的取代 API | 將變更的事實透過 `supersede_semantic_memory` 路由，而不僅僅依賴後續的衝突清理。 | 封存的記憶具有清晰的 `archive_reason`，且新行指向來源事件。 |
| 記錄更新審計事件 | 為每個候選記錄 `memory_update_decision` 事件。 | 可觀測性可以解釋為什麼一條記憶被添加、合併、取代或跳過。 |

### 優先級 5：在工具工作前檢索程序記憶 (Retrieve Procedure Memory Before Tool Work)

工作流/片段記憶目前已有儲存，但活動檢索上下文主要格式化語義記憶。程序記憶應幫助助手在新請求與過去工具工作相似時，重複使用已知成功的工作流。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 添加程序檢索上下文 | 建立 `build_procedure_context` 函數，按任務類型、詞彙相似度、成功率和近期程度對活動程序排序。 | 相似的工具請求會注入一個簡潔的「相關可重複工作流」章節。 |
| 結合語義和程序上下文 | 在嚴格的 token 預算和確定性排序下合併記憶體上下文章節。 | 最終提示詞包含使用者/項目事實和可重複工作流，而不重複不相關的歷史。 |
| 自動追蹤程序結果 | 在工具工作流成功或失敗後記錄 `procedure_result` 事件，然後將其餵入生命週期策略。 | 程序成功/失敗次數反映實際的後續重複使用情況，而非僅僅是初始建立。 |

### 優先級 6：改進記憶體治理和 CLI 操作 (Improve Memory Governance and CLI Operations)

可觀測性命令已經顯示了概覽、片段、訊息和技能運行。為了使記憶體可稽核且可修正，需添加明確的回顧命令。

| 任務 | 範圍 | 完成定義 |
|---|---|---|
| 添加回顧命令 | 擴展 `observability.py`，增加列出待處理候選、按類型分列活動事實、低信心事實、衝突和程序的命令。 | 維護者無需手動打開 SQLite 即可檢查記憶體質量。 |
| 添加修正命令 | 從 CLI 支持封存、確認、矛盾和取代操作。 | 命令寫入審計事件，預設永不硬刪除。 |
| 添加匯出/匯入 | 將語義和程序記憶匯出為 JSON 以用於備份或遷移。 | 匯出的記憶包含來源 ID、封存狀態、信心度和時間戳。 |

### 建議實施順序 (Recommended Implementation Order)

1. 將壓縮的工作記憶保留與現有的回顧管線連結。
2. 添加類型化/範圍化的語義記憶以及按類型的檢索格式化。
3. 在插入新語義記憶之前添加一等更新決策。
4. 添加程序檢索上下文和自動程序結果追蹤。
5. 添加實體表和別名感知檢索。
6. 添加 CLI 回顧/修正/匯出命令。

在考慮外部記憶體後端（如 Mem0, Cognee, Azure AI Search 或圖資料庫）之前，應完成前三個步驟。目前的 SQLite 設計對於驗證產品行為仍然足夠，主要風險在於記憶體質量而非儲存容量。

## 速率限制和請求預算計畫 (Rate-Limit and Request Budget Plan)

### 每輪預算 (Per-Turn Budget)

每個使用者輪詢應有明確的遠端請求預算。主 `run_agent` 完成優先權高於所有記憶體強化。記憶體相關工作在使用遠端完成或嵌入之前必須檢查預算。

建議初始限制：

| 操作 | 同步使用者輪詢限制 | 回退方案 |
|---|---:|---|
| 主助手聊天完成 | 必要，含現有重試/退避 | 若所有重試失敗，則顯示現有 API 錯誤。 |
| 用於記憶體檢索的查詢嵌入 | 1 | 僅使用詞彙排序。 |
| 缺失語義記憶嵌入補全 | 0 | 將嵌入放入背景隊列或使用雜湊嵌入。 |
| 輪詢後的語義提取 | 前台 0，背景小規模有界批處理 | 使用解析器回退並將候選留在隊列中。 |
| 程序相似度 LLM 比較 | 前台 0，僅針對背景模糊案例 | 使用精確或詞彙匹配器。 |
| 遺忘策略 | 0 | 僅使用確定性規則。 |

### 檢索流程 (Retrieval Flow)

檢索應分階段進行，使遠端嵌入呼叫次數不隨儲存記憶體數量增加而增長：

1. 僅獲取活動、未過期、未被取代的記憶體。
2. 應用廉價的詞彙或近期/信心度過濾，選出小規模候選集。
3. 在預算允許時，最多對使用者查詢執行一次嵌入。
4. 僅對具有現成快取嵌入的候選集進行排序。
5. 不要為每個缺失嵌入的記憶體同步生成嵌入。
6. 將缺失嵌入放入具有低併發、Retry-After 處理和退避機制的背景工作隊列中。

這避免了危險模式：一次使用者輪詢產生 `1 + N` 個嵌入請求（`N` 為無快取嵌入的活動記憶體數量）。

### 記憶體回顧流程 (Memory Review Flow)

記憶體回顧應採取盡力而為 (best-effort) 並與回應路徑解耦：

1. 同步記錄片段。
2. 使用本地 Laya 分類作為廉價閘門。
3. 在將語義提取或程序回顧放入隊列前，要求達到信心度閾值。
4. 預設在背景工作程序中運行提取和程序匹配。
5. 不要用 `join()` 阻塞每次輪詢；僅在優雅關機或明確維護時排空隊列。
6. 遇到 HTTP 429 時，遵守 `Retry-After`，指數級退避，並將片段保留在隊列中而非緊密重試。
7. 若預算耗盡，使用確定性回退或將候選保持在待處理狀態。

### 嵌入快取與補全 (Embedding Cache and Backfill)

語義記憶在生成嵌入後應將其儲存。補全應在互動路徑之外執行且必須有界：

- 使用低工作併發（例如 1）。
- 每隔一定時間處理小批次。
- 當提供者近期返回 429 時跳過補全。
- 排序時優先使用快取嵌入；僅將雜湊嵌入作為本地回退。
- 追蹤 `embedding_updated_at` 或等效元數據，以便刻意刷新陳舊嵌入。

### 可觀測性 (Observability)

系統應記錄足夠資訊以解釋記憶體行為而無需猜測：

- 每輪遠端聊天完成次數。
- 每輪遠端嵌入次數。
- 預算耗盡的回退次數。
- 背景隊列深度。
- 429 次數和 Retry-After 延遲。
- 因缺失嵌入而被跳過的記憶體數量。

## 設計原則 (Design Rules)

- Laya 是閘門，不是資料庫權威。
- 每條語義和程序記憶必須指向一個來源片段。
- 新記憶不會靜默覆蓋舊記憶；它們會帶著理由取代或封存舊記憶。
- 檢索應優先選擇活動、近期、高信心度的記憶。
- 如果記憶體儲存或 Laya 分類失敗，機器人應繼續工作。
- 記憶體功能不得產生無界的遠端 LLM 或嵌入請求。
- 主助手回應優先於語義提取、程序匹配、嵌入補全和遺忘回顧。
- 記憶體工作產生的遠端 429 應導致記憶體行為降級，而非終止聊天會話。
